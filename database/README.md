# database

PostgreSQL (+ pgvector) schema, migrations and seeds for Hacksgiving. Alembic owns
the schema ([ADR 0003](../docs/decisions/0003-alembic-migrations.md)); every
revision runs explicit SQL. Same migrations everywhere:

- **Local dev and tests**: `compose.yaml`, a pgvector Postgres container.
- **Staging and production**: two Supabase projects in the "Milwaukee
  School of Engineering" org, `hacksgiving staging` (`lkclzkolfiegzhejsagd`)
  and `hacksgiving` (`hdxumncrbngpwaedmonr`), both us-east-1. Only Postgres is used: no Supabase Auth, and
  the Data API is off.

## Layout

- `alembic.ini`, `migrations/env.py` — Alembic configuration. Settings come
  from the environment, never from the ini file.
- `migrations/versions/` — numbered revisions. Large ones keep their SQL in
  a `.sql` file of the same name (`0001_initial_schema.sql`).
- `seeds/local/` — the local-only dev user, loaded by
  `./migrate.sh --local` (`seeds/load.py`). Not migrations.
- `migrate.sh` — runs Alembic with the `api/` project's Python environment.
- `compose.yaml` — local-dev PostgreSQL + pgvector.
- `terraform/` — Supabase settings and connection secrets for both projects (see below).
- `.gitlab-ci.yml` — included from the root CI: plans/applies `terraform/`, then migrates staging and production.

## Schema

| Revision | What it does |
|---|---|
| `0001_initial_schema` | The `app` schema and `app.users` (the pgcrypto and vector extensions) |
| `0002_app_role` | Creates the API's role (`HACKSGIVING_APP_ROLE`, default `hacksgiving`) if missing and grants it the `app` schema. The API never connects as the owner |
| `0003_api_functions` | Every function the API calls, `app.<domain>_<verb>` ([ADR 0007](../docs/decisions/0007-sql-in-stored-functions.md)) |
| `0004_supabase_lockdown` | On Supabase only: no default grants to `anon`/`authenticated` in `public` |
| `0029_voice_safety_and_follow_up` | Safe callback plans, structured call-resume checkpoints, referral check-ins and voice impact funnel |

## The API's functions

The API holds no SQL. Each data operation is one function in `app`, named
`<domain>_<verb>` with `p_` parameters
([ADR 0007](../docs/decisions/0007-sql-in-stored-functions.md)). They run
with the app role's own grants (`SECURITY INVOKER`); revision 0002's
default privileges give it `EXECUTE` on new functions.

To change one, add a revision that replaces it (`CREATE OR REPLACE
FUNCTION`, or drop and create when its signature changes) and list any new
function in that revision's downgrade.

## First start

Needs Docker and `uv`.

1. `cp .env.example .env`. Keep `HACKSGIVING_APP_PASSWORD` equal to
   `APP__DATABASE__PASSWORD` in `api/.env`.
2. Create the shared Docker network if it doesn't exist yet:
   ```bash
   docker network create hacksgiving
   ```
3. Start Postgres and migrate, with the local dev user:
   ```bash
   docker compose up -d postgres
   ./migrate.sh --local
   ```

`./migrate.sh` alone upgrades without local seeds. Other arguments go
straight to Alembic: `./migrate.sh current`, `./migrate.sh history`,
`./migrate.sh downgrade -1`.

## Adding a migration

```bash
uv run --project ../api alembic revision --rev-id 0005 -m "add widgets"
```

That writes `migrations/versions/0005_add_widgets.py`, already
pointing at the previous head. Put the SQL in a `.sql` file of the same name and run it with
`context.config.attributes["run_sql_file"](__file__)`. Write the downgrade too:
`api/tests/integration/test_migrations.py` runs every revision up, down and up
again. Never edit a revision that has been applied anywhere.

## Supabase

`terraform/` (state `hacksgiving-database-prod`) manages both projects:

- **SSL** enforced, and the **Data API off** (no schemas exposed).
- **The API's role password**, one per environment, generated by Terraform.
- **Vault secrets** for each environment. Production uses
  `secret/deployments/hacksgiving/…` and staging `secret/deployments/hacksgiving/staging/…`:

  | Key | Contents | Read by |
  |---|---|---|
  | `db-migration` | Session pooler (5432) as `postgres.<ref>`, plus `app_username`/`app_password` | `migrate-*` jobs |
  | `db` | Transaction pooler (6543) as `hacksgiving.<ref>` | The API's ExternalSecret (`APP__DATABASE__*`, SSL on, no prepared statements) |

The projects themselves aren't in Terraform. Set their admin passwords by
hand and store them at `<prefix>/supabase-admin` (`password`).

### Pipeline

| Job | When |
|---|---|
| `db-plan` | Automatic when `database/` changes (on `main`, or on a branch that differs from `main`) |
| `db-apply` | Manual, default branch only, after `db-plan` |
| `migrate-staging` | Automatic on the `staging` branch, after `api-test`; `tf-apply-staging` waits for it |
| `migrate-production` | Manual, default branch only, after `api-test`; `tf-apply` waits for it |

All of them run as `gitlab-hacksgiving-database-ci`, whose paths are listed in
`infra/vault-config/vault-app-projects.tf` (`db_read`, `db_write`).

### Supabase access token

CI uses a scoped personal access token stored at
`secret/deployments/hacksgiving/supabase-terraform` (`access_token`). Create it under
Supabase Account → Access Tokens, scoped to the hacksgiving org's two projects, with:

- Connection Pooling (Read)
- SSL Enforcement (Read-write)
- Data API Config (Read-write)

The migrate jobs run Alembic from the `api/` project's environment (see the
header of `.gitlab-ci.yml`).
